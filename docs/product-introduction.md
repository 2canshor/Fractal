# Fractal in One Competition Project

Carson opens Fractal and says:

> I want to enter HKICTA with an app that helps students notice hidden emotion in messages.

Fractal becomes the environment for that Project.

## 1. Turn the idea into a Project

Fractal records the sentence as the **Brief**. The agent researches the competition rules, intended users, existing approaches, privacy risks, technical limits, and the evidence judges will expect.

One choice changes the whole product, so Fractal asks:

> Should the first version help friends and classmates, or trained counsellors?

Carson chooses friends and classmates. Fractal uses that answer to prepare a **Project Direction** and Carson approves:

- **Goal:** submit a working, evidence-backed app that helps students recognise emotional subtext;
- **Success Criteria:** the core flow works, real user testing supports the claim, the pitch matches the product, and every submission file meets the rules;
- **Priorities:** user value first, reliable evidence second, presentation polish third;
- **Project Plan V1:** research, prototype, user test, build, verify, and prepare the submission.

The Plan gives each stage an expected effort. The first prototype is a Milestone Review Point. Twenty hours of interface work is an Exception Review threshold.

## 2. Reach a milestone and zoom out

The research and first prototype are complete. Fractal opens a **Milestone Project Review**.

The prototype caused the review, but Fractal checks the whole Project:

- the Goal still matches the competition;
- the Success Criteria still describe a strong submission;
- research evidence is useful;
- the prototype proves the basic flow;
- user testing is scheduled too late;
- interface polish is already using time intended for evidence collection;
- the pitch and submission files have not started;
- six weeks remain.

Fractal compares the work with Plan V1 and recommends moving user testing before further polish. Carson keeps the Goal and Success Criteria. Fractal records **Plan V2**, together with the readable V1 → V2 difference.

## 3. Hit an exception and protect the whole Project

Later, responsive testing reaches the twenty-hour interface threshold. The same layout repair has also appeared in three Work Signatures. Fractal opens an **Exception Project Review**.

The review checks more than the layout:

- the shared layout rule is causing several screen failures;
- user testing has started and supports the product direction;
- the evidence write-up is one week behind Plan V2;
- the pitch still needs a judge-facing story;
- the core feature works;
- one real-device test remains;
- three weeks remain.

Fractal recommends repairing the shared layout rule once, testing four representative screen sizes, and then returning effort to evidence and the pitch. It records **Plan V3** and the biggest remaining concern: the evidence write-up could become the new bottleneck.

## 4. Finish the competition entry

Work continues against Plan V3. Fractal links evidence to each Success Criterion and shows the Project as ready for completion. Carson checks the app, testing evidence, pitch, and submission package, then declares **Project Completion**.

The current-Project job is finished. Fractal now studies how it should handle future Projects better.

## 5. System Review Step 1 — Find Problems

System Review starts with the entire Project history: all three Plans, both Project Reviews, work records, corrections, evidence, outcomes, and resource use.

Project Assessment records both directions of change.

**Positive Delta**

- the Milestone Review moved user testing earlier than in Carson's previous competition Project;
- the Exception Review protected time for evidence and the pitch;
- the shared layout repair solved four screens together;
- the final pitch matched the tested product claim.

**Negative Delta**

- visual work exceeded its expected effort;
- the evidence write-up fell one week behind;
- the same layout symptom was repaired three times before the shared cause was addressed;
- the first Plan placed testing too late.

Issue Scan now uses **Quantity over Quality**. It collects broadly before explaining anything:

- the first prototype looked convincing before any user had tested it;
- one judge requirement was checked twice;
- two useful test comments never entered the pitch notes;
- responsive work used twenty hours;
- three layout repairs touched different screens;
- the evidence write-up started late;
- the Milestone Review changed the order of work;
- the Exception Review arrived after repeated repairs;
- the final real-device test found no new problem;
- the privacy explanation took much less time than expected;
- one research source was never used;
- Carson answered one product question much faster after seeing a prototype.

Some observations may become important; some may be noise. Fractal keeps them long enough for the next step to decide.

## 6. System Review Step 2 — Find Local Patterns

Project Patterns asks why the observations happened and separates symptoms from plausible causes.

It finds two useful local patterns:

1. **Evidence arrived after presentation decisions.** The late write-up and unused test comments are symptoms. A plausible common cause is the Plan sequence: evidence synthesis had no checkpoint before pitch work.
2. **Screen-by-screen repair hid a shared layout rule.** The three visible failures looked different, but their evidence points to one proximate cause. The real-device test is a counterexample showing that not every screen concern belonged to that cause.

The review labels both causes as evidence-supported interpretations rather than certainty.

## 7. System Review Step 3 — Compare history

Fractal compares this Project with previous Projects, System Reviews, proposals, Plan changes, and outcomes.

It finds a reversal:

- an earlier review made planning more detailed because important work was missed;
- a later review made planning shorter because setup took too long;
- the current Project again missed the right timing for evidence synthesis.

The pattern is not simply “Plans need more detail” or “Plans need less detail.” Reversal Check asks:

> Are we solving the wrong problem?

The possible hidden dimension is **when evidence must be reviewed before the Project moves to presentation work**.

Cause Research investigates that question in two independent directions:

- **External Research** checks credible competition, product-testing, and evidence-planning guidance;
- **Internal Review** checks Carson's actual Plan versions, Review Points, work order, and outcomes across Projects.

External evidence favours early evidence loops. Internal evidence shows that the required tasks were already written in the Plans; the missing part was a Review Point between testing and presentation. Reconciliation concludes that Plan length is probably not the main cause. The stronger hypothesis is stage-transition timing.

## 8. System Review Step 4 — Choose the response

Improvement Options checks what the current system can already do:

- delete a repeated planning reminder;
- shorten the generic competition checklist;
- merge two overlapping evidence prompts;
- simplify the Plan template;
- modify the existing Project Review so a Project can place an evidence checkpoint before presentation work;
- add a new competition-planning agent;
- keep the current system.

The existing Review Point and Project Review can express the useful change. The leading option is therefore a small modification to the existing planning guidance, tested as an experiment. Fractal records why the other options are weaker for this evidence.

Repetition Awareness contributes the three layout Work Signatures. Curiosity contributes the stage-transition idea. Their evidence stays inside this System Review decision.

## 9. System Review Step 5 — Reality Check

Fractal steps back and asks whether the proposed change would improve Fractal or merely change its wording.

- **Expected Effect:** Projects with testing evidence and a later presentation stage should review the evidence before presentation work begins.
- **Local Effect to test:** fewer late evidence rewrites in the next comparable competition Project.
- **Global Effect to test:** better final evidence without adding unnecessary reviews to unrelated Projects.
- **Historical comparison:** detailed and concise planning changes both missed the timing problem.
- **Main risk:** an automatic checkpoint could interrupt Projects whose evidence and presentation naturally develop together.

Because the proposal changes planning behaviour across future Projects, Two-Sided Review is warranted.

- **Case For:** the current mechanism already supports a well-placed Review Point, and local history shows a repeated timing cost.
- **Case Against:** one competition Project is a small sample, and a universal checkpoint could add friction.

Final Assessment recommends an **Experiment**: use the evidence checkpoint in the next comparable competition Project, with a clear stop condition and no change for unrelated Projects. Biggest Remaining Concern is the small comparison history.

Fractal presents four possible result types—Change Proposal, Experiment, Need More Evidence, and No Change—and records **Experiment** for this review. Carson sees the evidence, the alternatives, and the concern, then makes **Your Decision**.

If Carson approves the experiment, its later record keeps the original hypothesis, before state, Expected Effect, Local Effect, Global Effect, side effects, uncertainty, and actual outcome. A later System Review can then tell whether Fractal genuinely improved, whether the local effect caused global harm, or whether the result came from a different cause.

This is Fractal in use: it keeps the whole competition Project healthy while Carson is building it, then uses the completed history to improve how the next Project is handled.
